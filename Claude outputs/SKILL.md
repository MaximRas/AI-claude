# Задача → автотесты для API (metapix-api-tests)

## Конвенции фреймворка
- Репозиторий: `metapix-api-tests` (Python 3.10+, requests + pytest + pydantic v2, OpenAPI-контракт, Allure).
- Сервисы: auth-manager, object-manager (+ device / watchlist / chartilla), layout-manager.
- Клиенты: `services/<svc>/client.py`; фикстуры и фабрики: `tests/fixtures/`; тесты: `tests/<domain>/`.
- Спеки: `specs/<service>.json`; пути в тестах пишутся ровно как в спеке.
- Окружения: `config/config.yaml` (alphatest1, object-ng, dev-dw, staging, ...), выбор через `TEST_ENV`.
- **Как писать сами тесты — строго по `.claude/skills/api-autotest-writer/SKILL.md`.** Этот Skill
  отвечает за процесс, тот — за код тестов.
- Трекер и MR: GitLab `gitlab.dev.metapixai.com`; ключ задачи — `<проект>#<номер>` (например, `admin#596`).
- `.env` не читать и не коммитить.

## Где лежат артефакты
- Рабочие файлы разбора: `reports/<ключ-задачи>/` (impact.json, impact.md, test_plan.json).
  Ключ в имени папки пишется через дефис: `reports/admin-596/`.
- Итоговый отчёт: `docs/reports/<ГГГГ-ММ-ДД>_<сервис-или-стенд>_<тема>.md`
  (например, `docs/reports/2026-11-03_object-ng_backend2.md`).
- Чужие файлы в `reports/` и `docs/reports/` не перезаписывать.
  Зачем: параллельные разборы разных задач (или сессий) не затирают друг друга.

## Шаги
1. Прочитать задачу и все комментарии к ней.
2. Посмотреть связанные задачи, а также блокирующие её и блокируемые ею. Из них взять контекст:
   почему делается изменение и что ещё может его затронуть.
3. Посмотреть diff MR:
   - `python -m tools.mr_impact --repo <путь к сервису> --base <base-ref> --json reports/<ключ>/impact.json --md reports/<ключ>/impact.md`
   - затем прочитать сам diff (`git -C <репо> diff <base>...HEAD`), потому что отчёт эвристический
     и может что-то пропустить.
4. Проанализировать изменения и составить план в `reports/<ключ>/test_plan.json`
   (формат как у `api-impact-analyzer`): эндпоинт, new/changed/removed, действие, кейсы с «почему».
   → **Стоп: показать план таблицей и дождаться подтверждения.**
   Зачем: ошибку в анализе дешевле поймать до того, как написан код.
5. Написать, изменить или удалить тесты по плану, следуя `api-autotest-writer`.
   Новые тесты помечать `@pytest.mark.generated`.
6. Проверить работоспособность:
   ```bash
   ruff check . && ruff format --check .
   pytest -m selftest -q
   pytest --collect-only -q <изменённые файлы>
   python -m tools.coverage --service <svc> --uncovered
   TEST_ENV=<стенд> pytest <изменённые файлы> -q    # если есть доступ к стенду и креды
   ```
7. Исправить ошибки, если они есть (не больше 3 попыток, см. правила).
8. Написать итоговый отчёт в `docs/reports/...` по формату ниже и коротко пересказать его в чате.

## Формат

### План (шаг 4)
| Эндпоинт | Статус | Что изменилось | Действие | Кейсы |
|---|---|---|---|---|
| PATCH /watchlist-manager/public/v1/watchlists/{id} | changed | новое поле `color` | update_tests | happy + contract, 422 неверный enum, дефолт |

### Итоговый отчёт (шаг 8)
```markdown
# <ключ задачи> — <тема> (<ДД.ММ.ГГГГ>)

- Стенд: <TEST_ENV, URL API>
- Задача: <ссылка> · MR: <ссылка> · Риск: low / medium / high
- Скоуп: <что проверялось>

## Что меняет MR в API
- 2–4 пункта; отдельной строкой: Breaking changes — список или «нет»

## Итог: <N> проверок
| Группа / эндпоинт | Результат |
|---|---|

## Находки
### 1. <Что сломано> → <факт> вместо <ожидание> (<Severity>, <регрессия | не регрессия — есть и на alphatest1 | на alpha не проверено>)
```bash
TOKEN=<access-token после login + PATCH /auth-manager/context/active-company>
curl ...   # минимальное воспроизведение
# факт: ...; ожидание: ...
```
(«нет», если находок нет)

## Автотесты
| Добавлен / Изменён / Удалён | Файл::тест | Зачем |
|---|---|---|
Прогон: что запускалось, результат (passed / failed / skipped), что не удалось запустить и почему.
Команда для регресса: `TEST_ENV=<стенд> pytest ...`

## Непроверенные предположения
- например, «эндпоинта ещё нет в спеке, контракт взят из кода»

## Ручные проверки
- то, что не проверить API-тестом

## Данные
- Что менялось на стенде и как восстановлено; возможные следы.
```

## Правила

### Честность тестов
- **Не ослаблять проверки, чтобы тест прошёл.** Если тест падает из-за бага бэка, пометить его
  skip/xfail со ссылкой на задачу и записать баг в «Находки».
  Зачем: тест, подогнанный под баг, закрепляет баг как норму, и находка теряется.
- Источник правды — задача и diff. Если ожидаемое поведение неясно, задать вопрос и не угадывать.
  Зачем: тест на угаданное поведение проверяет догадку, а не требования.
- Изменение контракта сначала квалифицировать: намеренное оно или breaking change.
  Только намеренное изменение даёт право менять ассерты.
- Если MR ещё не задеплоен, падение с 404 на новый эндпоинт ожидаемо. Его нужно отметить
  в отчёте, а не «чинить».

### Находки
- У каждой находки есть severity (Blocker / Critical / Major / Minor / Trivial), отметка, регрессия ли
  это, и минимальный curl-репро с «факт / ожидание». Токен в curl — только плейсхолдер.
  Зачем: разработчик воспроизводит баг за минуту, без переписки.
- «By design» не считать дефектом; явно написать, почему это by design.

### Данные стенда
- Всё, что тест или ручная проверка меняет на стенде, восстанавливать (cleanup / фабрики),
  а в разделе «Данные» отчёта перечислять, что было изменено и восстановлено.
- На прод-юзерпуле не создавать и не удалять пользователей (маркер `user_pool_mutation`).

### Границы работы
- **Трогать только тесты в рамках задачи** и не рефакторить попутно.
  Зачем: MR остаётся маленьким, его легко ревьюить, и не ломается чужое.
- Удалять тест и метод клиента, только если эндпоинт или поведение действительно удалены в diff.
- `framework/` не трогать без необходимости. Если без этого никак, менять минимально,
  добавить selftest и описать в отчёте.
- Эндпоинты из `tools/coverage_ignore.yaml` не покрывать без явной просьбы.
- **Если тест всё ещё падает после 3 попыток исправления, остановиться** и описать проблему:
  что пробовал, текст ошибки, гипотезу о причине.
  Зачем: так нет бесконечного цикла правок, а решение возвращается человеку.

### Единое покрытие
- Для каждого изменения пройти чек-лист кейсов из `api-autotest-writer` (happy + contract,
  дефолты, 422, 404, auth, бизнес-ошибки, пагинация, права). Неприменимый кейс указать
  в плане с причиной.
  Зачем: покрытие одинаковое от задачи к задаче.
- На каждый успешный ответ ставить `.assert_contract()`, а не только проверять статус.
  Зачем: тест ловит поломку контракта, а не только падение сервера.
